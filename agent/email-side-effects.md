# 外部调用与邮件补发

## 发信成功后，任务还没更新

Agent 已生成结果，worker A 调用邮件服务并收到成功响应，还没记录发送结果或把任务改成 `completed` 就崩溃。worker B 接管时，需要决定是否重新发信。把 Agent 结果先持久化，可以单独恢复发信步骤。

共享存储里的发送状态和邮件服务回调都能提供确认。如果成功回调已经落库，B 可以跳过发信并补写任务状态。回调可通过队列交付，但 B 接管时回调可能还没到或还没被消费。此时本地缺少成功记录，邮件仍可能已经发出。

## 邮件服务支持幂等键

1. 首次发送前，保存发信记录和幂等键。若每个任务只有一封结果邮件，可以用 `task_id + ':result-email'` 表示这次逻辑发送。
2. A 和 B 对同一次逻辑发送使用同一个幂等键。在服务商的去重有效期和适用范围内，重复请求会被视为同一次发送。
3. 收到成功响应或回调后，持久化发送结果。成功响应或回调确认了哪个阶段取决于服务商，常见的阶段包括服务已接受请求和邮件已投递。

## 邮件服务缺少去重和结果查询

假设服务商没有幂等键，无法按业务 ID 查询发送结果，回调还可能延迟或丢失。B 看到记录停在 `sending` 时，可以先等待一段时间。等到成功回调就确认发送，减少因回调延迟产生的重发。等待超时后将状态标为 `unknown`，表示此时缺少确认。

如果 `unknown` 后停止自动重发，可以避免系统重试造成重复邮件，同时接受邮件可能实际未发出的代价。如果选择在超时后重发，就要接受第一封可能已经发出、用户可能收到两封的风险。等待窗口只改变决策时机，无法消除这个取舍。

## 超时写入遇到迟到回调

`unknown` 之后仍允许可信的迟到成功回调将同一次发送改为 `sent`。回调按发送记录关联，重复回调应幂等处理，避免重复触发后续动作。

超时检查可能先读到 `sending`，而回调在它写入前已经改成 `sent`。把预期状态放进同一条更新语句。

```sql
UPDATE email_send
SET status = 'unknown'
WHERE id = ? AND status = 'sending';
```

回调先落库时，超时更新影响 0 行。超时先落库时，成功回调仍可把 `unknown` 改为 `sent`。这和[并发领取任务](../mysql/innodb-task-claim.md)用的是同一种条件更新。

## 人工补发与按次追踪

客服在首次发送为 `unknown` 时提交补发，随后第一次的成功回调才到。首次成功足以更新任务层面的「至少一次发送成功」。每次发送仍应独立存一条记录，回调只更新其关联的发送记录。这样可以同时看到首次发送是 `sent`，补发仍在排队或等待确认。

| 第一次成功回调落库时，补发的进度 | 处理方式 |
| --- | --- |
| 补发仍在队列，尚未交给邮件服务 | 可以从 `queued` 改为 `skipped`，保留原因「原发送已确认成功」 |
| 补发已经交给邮件服务 | 继续跟踪补发结果，用户仍可能收到两封邮件 |

在补发 worker 调用邮件服务前检查原发送结果，可以跳过已无必要的补发。如果成功回调在这次检查之后才到，补发仍可能发出。回调处理阶段过滤掉一次数据库更新，无法撤回已经提交给邮件服务的请求。
