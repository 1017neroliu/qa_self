# 工具调用与重试

## 模型发出调用请求，Go 执行业务查询

用户问「任务 842 处理完了吗？」Go 服务第一次请求模型时，提供用户消息和可用工具的定义。工具定义写明 `get_job_status` 的用途、参数 `job_id` 的类型和是否必填。

1. **模型提出调用。** 例如返回工具名 `get_job_status`、参数 `{"job_id": 842}` 和本次调用标识 `call_1`。此时业务查询尚未执行。
2. **Go 执行查询。** 校验工具名、参数和当前用户的任务访问权限，再调用业务接口。查询结果可以包含 `processed: 800`、`total: 1000` 和 `status: running`。剩余数量可以由总数减去已处理数。
3. **Go 把结果交回模型。** 下一次模型请求带上工具结果，并用 `call_1` 关联先前的调用。模型据真实数据答复「任务仍在处理，已完成 800 条，共 1000 条」。

如果工具超时，Go 可以向模型返回结构化错误 `QUERY_TIMEOUT`。用户看到的是「查询任务 842 状态超时，暂时无法确认进度」。服务端日志记录请求 ID、任务 ID、耗时和超时位置。需要协助排障时，用户可以提供请求 ID。

## 只读查询怎么重试

`get_job_status` 适合由 Go 工具执行层对临时故障做有限重试。参数无效、权限不足或总期限耗尽时结束调用。每次尝试的耗时和间隔都计入总预算。例如工具预算为 1 秒，第一次查询最多用 400 毫秒，再等 100 毫秒，第二次最多只用剩余时间。仍未查到时，把结构化错误交回模型。

## 创建任务超时怎么重试

`start_job` 有副作用。第一次请求超时后，先查与该操作对应的任务。如果找到了，返回已有的 `job_id`。如果没找到，第一次请求仍可能正在创建任务。即使查的是主库，直接重发也可能创建两条任务。

如果创建接口由自己控制，可以用数据库唯一约束按调用方身份和幂等键原子去重。并发请求携带同一个键时，创建端可以返回已有 `job_id`，或在首次操作仍在处理中时告知调用方稍后查询。任务处于 `running` 时，创建动作本身可能早已成功。这里和[邮件发送结果未知](email-side-effects.md)面对的是同一种问题。

| 情况 | 幂等键怎么用 |
| --- | --- |
| 浏览器超时，重发同一次点击的请求 | 浏览器在第一次发出请求前生成键，重发时沿用 |
| Go 调下游超时，重发同一次创建操作 | Go 对这次操作持续使用同一个下游幂等键 |
| 用户主动要求再跑一次，即使参数完全相同 | 为新操作生成新键。新操作自身超时重发时沿用这个新键 |

API 可以用 `POST /jobs` 创建，用 `POST /jobs/{id}/rerun` 表达主动重跑。重复请求返回的是同一次创建操作对应的任务。同样的参数可能引用已变化的数据集，也可能使用新版处理逻辑，因此仅比较参数无法识别用户是否发起了新操作。

`Idempotency-Key` 标识一次逻辑操作，日志里的 `request_id` 标识一次 HTTP 请求。同一次点击重发两次时，可以有两个日志 ID 和一个幂等键。如果每次都由 Go 收到 HTTP 请求后现场生成新键，Go 就无法凭这个键知道两次请求来自同一次点击。
