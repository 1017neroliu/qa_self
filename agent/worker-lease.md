# Worker 租约与任务回收

## 领取后进程崩溃

Go worker A 将任务改成 `claimed` 并提交，随后在真正执行前崩溃。如果其他 worker 只查询 `pending`，这条任务就会一直停在 `claimed`。

给任务设定固定的执行超时可以回收一部分任务，但也可能打断仍在运行的慢任务。系统暂时收不到响应时，仅凭超时无法区分进程崩溃、网络中断和长耗时执行。

## 租约、心跳与接管

1. **领取**。在写入 `claimed` 时一起写入 `lease_until` 和本次领取唯一的 `claim_token`。
2. **续租**。执行任务的同时定期续租。例如租约 60 秒，每 15 秒续一次。续租条件要求 token 匹配、任务仍在执行且租约尚未过期。心跳可以独立于一次耗时的模型调用运行。
3. **接管**。租约到期后，其他 worker 可以用条件更新接管任务。检查租约已过期和写入新租约、新 token 必须属于同一次原子更新。
4. **提交结果**。按 `claim_token` 验证领取身份，必要时一并检查租约仍有效。如果 B 已接管，A 用旧 token 提交结果时，条件更新会影响 0 行。

A 可能因为网络中断或暂停而错过续租，恢复后仍继续执行。租约可以限制谁能提交任务状态，但已经发出的外部调用仍可能生效。如果 A 已经调用邮件服务，B 接管后要单独判断如何处理这一步。见 [外部调用与邮件补发](email-side-effects.md)。
