# InnoDB 并发领取任务

## 两个请求读到同一条任务

标注平台从 `annotation_task` 表里按 `id` 取第一条 `pending` 任务。A 和 B 各自在事务内执行普通 `SELECT`，都读到了同一个 `id`。

如果后续只用 `WHERE id = ?` 更新，A 先获得该行的写锁，B 等待。A 提交后，B 的更新条件仍然成立，可以覆盖领取人。两个请求都可能报告成功。这个时序只有 B 等 A，属于锁等待。死锁需要出现循环等待，例如 A 和 B 各自持有一把锁，同时等待对方持有的锁。

把领取资格放入更新条件，复用已有的 `status` 字段。

```sql
UPDATE annotation_task
SET status = 'claimed', assignee_id = ?
WHERE id = ? AND status = 'pending';
```

A 提交后，B 按记录的当前状态检查条件，发现已经是 `claimed`，所以影响 0 行。只有影响 1 行且事务提交成功，应用才确认领取成功。如果 A 回滚而任务仍是 `pending`，B 可以成功领取。

## 隔离级别和重试的事务边界

MySQL InnoDB 默认使用 `REPEATABLE READ`（RR，可重复读），实例和会话可以配置其他隔离级别。以下假设 B 第一次执行普通 `SELECT` 时，A 的领取尚未提交。随后 A 提交，B 的条件更新影响 0 行，期间没有人把任务改回 `pending`。

| B 接下来执行原来的普通 `SELECT` | RR | RC（`READ COMMITTED`，读已提交） |
| --- | --- | --- |
| 在同一个事务里查询 | 沿用第一次一致性读建立的快照，仍可能查到原任务 | 使用新快照，可以看到 A 的提交，原任务被过滤 |
| 结束当前事务，在新事务里查询 | 建立新快照，原任务被过滤 | 使用新快照，原任务被过滤 |

事务边界就是事务的开始与结束。采用普通查询加条件更新时，可以把「查候选任务 → 尝试领取」放在一个事务里。影响 0 行就结束该事务，再启动下一次尝试。RR 下在原事务里直接循环普通 `SELECT`，可能反复选中同一条任务。条件更新返回 0 行时，如果曾因另一事务持有记录锁而等待，这次等待已经发生在 `UPDATE` 中。

RC 下更新同一条记录仍会争用记录锁。间隙锁保护的是索引记录之间的区间，和本题中对同一条已有记录的写入争用是两件事。SQL 恢复执行后，还要检查更新条件是否成立。

## 用 `SKIP LOCKED` 领取其他任务

MySQL 8.0 中，假设有 `(status, id)` 索引，有两条待领取任务 1 和 2。A 已用下列查询锁住任务 1，仍在事务中。

```sql
SELECT id
FROM annotation_task
WHERE status = 'pending'
ORDER BY id
LIMIT 1
FOR UPDATE;
```

- B 执行相同查询，通常会等待任务 1 的锁。假设无其他事务干扰且等待未超时，若 A 将任务 1 改为 `claimed` 后提交，B 会继续选任务 2。若 A 回滚，B 可以选任务 1。
- B 改用 `FOR UPDATE SKIP LOCKED`，可以跳过任务 1，选中并锁住任务 2。前提是任务 2 可用且能获得所需的锁。
- 用于领取时，锁定查询和写入领取状态应在同一事务内完成。跳过被锁的任务意味着并发领取时允许暂时越过较小的 `id`。
